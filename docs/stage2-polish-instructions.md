## 2. 作業の決まり

`docs/stage2-finish-instructions.md` 2 章と同じです。要点だけ書きます。

- Open-Meteo へ通信しない。通信してよいのは `sync` の `git fetch origin data` だけ。Web 検索・ページの取得をしない。GitHub Actions を起動しない。
- commit まで。push・PR・マージは利用者。ほかのビヨリのフォルダは読むだけ。
- `collect/`・計測フック・Stop フック(`concierge/stop_hook.py`・`.claude/`)は変えない。
- `git add -A` を使わない。コマンドのパスは `/` で書く。外部ライブラリを足さない。
- **既存のテストの期待値を、通すために書き換えない。** 例外は、3.1 と 3.4 に名前を書いたテストと、3.2・3.6・3.8 の変更で値が変わることを確かめているテストだけ。例外で変えたテストは、名前・変えた行・理由を報告書に並べる。
- 山についての知識を、コード・設定・見本に自分の知識で書き込まない。
- commit の前に必ずテストを実行する。

**止まる条件**

1. 追跡中のファイルに未 commit の変更がある(`git status --porcelain --untracked-files=no` が空でない)。
2. main に仕上げが入っていない(`concierge/stop_hook.py` が無い)。
3. 変更前のテストが通らない(270 件のはず)。
4. 上の例外に当たらない既存のテストの期待値を、書き換えないと通せない。このときは、その項目の変更だけ commit せず、分かったことを報告書に書いて、ほかの項目は進める。

## 3. 第 1 部: 直す 8 点

始める前に: `git status`・main であること・`git log -1`・テストの件数・`python -X utf8 -m concierge sync` と `status`(棚の時点)を控える。`git switch -c feature/stage2-polish`。この指示書(`C:/temp/biyori-concierge-stage2-polish-instructions.md`)を `docs/stage2-polish-instructions.md` に写して commit。

### 3.1 見送りの文の「点数がいちばん高い」にも検査を当てる

- `concierge/data/verify.yaml` の `compare.score_skip` を `[]` にする(コメントも、利用者が決めたことに合わせて直す)。
- `tests/test_concierge_answer.py` の `test_pick_rules` の最後の 3 行(「点数がいちばん高い横岳は、今回は見送るのがよさそうです。」が合格することを確かめている)を書き換える。
  - 同点のある山を「点数がいちばん高い」と書いた見送りの文は、`comparison_tied` で不合格になること。
  - **もとのテストが守っていたこと**(見送りの文は、おすすめの語の検査 `pick_undeclared` で止めない)は、別の文で確かめ続ける。例: 同点のない 1 位の山を「点数がいちばん高い○○は、今回は見送るのがよさそうです。[順位の事実の印]」と書いた文が合格すること。見本にその形の山が無ければ、最上級を使わない見送りの文(「○○は、今回は見送るのがよさそうです。[印]」)で確かめる。

### 3.2 見送りの枠の並び

`concierge/brief.py` の `skip_key` を、次の順にする。

1. 危険の段階の重い順(危険 → 警戒)。山に危険信号が 2 つ以上あるときは、いちばん重い段階で比べる。同じなら、その段階の危険信号の数の多い順。
2. 点数の高い順。
3. 出発地からの直線距離の近い順。
4. 山の ID の順。

`config.yaml` のコメント(並びの説明)と、控えの文(`concierge/fallback.py`)の見送りの並びも合わせる。テスト: 100 点で「危険」の山が、近いだけの「警戒」の山より先に入ること。

### 3.3 枠に入らなかった危険な山の件数

- 日ごとに、基準点以上で危険信号が「警戒」「危険」の山の件数を、段階ごとに数える(見送りの枠に入った山も、入らなかった山も合わせた全体の件数と、枠の外の件数)。段階は、山のいちばん重い段階で数える。
- この件数を、日ごとの事実として資料に持たせる(id の形は今の決まりに合わせる。比べた結果の `C…` と混ぜるか、新しい字にするかは実装で決め、印の正規表現に足す)。`say` に書いてよい言い方を持たせる(例: 「危険信号が警戒以上の山は 30 座」「このうち危険は 12 座」)。
- 照合: 「どれも」「全部」「すべて」「どの山も」(仮置きの一覧)と危険信号の語が同じ文にあるときは、この件数の事実の印が要り、文の言っている範囲が件数と合うこと(枠の 3 座だけを見て「どれも強風危険」と書いた、仕上げの問い 8 の誤りを止める)。合うかどうかを機械的に決められない言い方は止める側に倒し、直し方として「件数を書く」を示す。
- スキーマは項目を足すだけ(版は `/1` のまま)。資料の Markdown にも出す。

### 3.4 順位の項目を 1 つにまとめる

- `rank` を「その日の順位(同点は同じ順位)」の意味にする。`day_rank` はやめ、`day_rank_ties` は `rank_ties` にする(名前は実装で決めてよいが、順位を表す項目は 1 つだけにする)。並び順そのものは、資料の `facts` の順で表す。
- `tests/test_concierge_answer.py` の `test_schema_and_candidates` の、`rank` を並び順の番号(1, 2)として確かめている期待値を、同点の順位に合わせて書き換える(90.4 点で同点の八ヶ岳(赤岳)と横岳は、どちらも同じ順位)。
- スキーマ `schemas/biyori-brief.schema.json` の項目の名前と意味が変わる。**版は `/1` のままにし、変わったことを `CHANGELOG.md` と報告書に書く**(資料は PC の中で作ってすぐ使うもので、ほかのリポジトリは読まない。古い資料は作り直せば済む)。古い資料を `verify` に渡したときに、分かりにくいエラーで止まらないこと(「資料を作り直してください」と出る)。

### 3.5 種類を書かない「危険信号が警戒まで出ています」

`concierge/verify.py` の `hazard_mismatch`: 危険信号の種類(強風・低体温症・雷)を書かずに段階だけを言う文は、印の事実の**いちばん重い段階**と合っていれば通す。合っていなければ今までどおり止める。通る言い方の形(「警戒まで」「警戒以上」「危険の」など)は仮置きの一覧にし、`docs/answer-checks.md` に書く。

### 3.6 答えに出る名前(2 つだけ)

- `cloud_pct_raw`(山頂雲量(予報そのまま)): 答えに書いてよい表記(`say`)から外す。資料の JSON の値としては残してよいが、資料の Markdown の「書いてよい値」には出さない。
- `cape`(雷リスク(CAPE)): 値を `say` から外す。山ごとの危険信号の文(`_hazard_line`)は「雷注意」「雷警戒」のように段階だけにし、`(CAPE … J/kg)` を付けない。
- `docs/brief-fields.md` の表に、「答えに出さない値」として 2 つを残す(理由と、利用者の決定 2026-11-23)。
- 「雨天割合(活動時間)」「視程(稜線)」は変えない。

### 3.7 合間にも作業の説明を書かない

利用者の試しで、答えの前に「照合に合格した答えを、送る前に最終確認しています。」という文が出た。最後の答えの一部ではないので Stop フックは止めないが、利用者の画面には出る。

- `AGENTS.md`(手順の 5・6 のあたり)と `.claude/skills/biyori-concierge/SKILL.md` に足す: コマンドを呼ぶ合間にも、作業の説明・進み具合の文を書かない(「資料を作ります」「照合に合格しました」「最終確認しています」など)。答えの前に利用者に見せる文は、`verify` の出した文だけ。
- `verify` に合格したあと、もう一度確かめるためのコマンドを足さない(合格したら、その標準出力をそのまま送る)。
- フックでは検査しない(合間の文は Stop フックの対象外。手順として守る)。そのことを `docs/stop-hook.md` に 1 行足す。

### 3.8 危険信号の注記の位置

利用者の試しで、「危険信号は、点数とは別に出る警告です。」が、危険信号の出ていない山(高尾山)の説明の下に置かれた。

- `docs/answer-voice.md` と資料の Markdown の注に足す: 注記は、最後の危険信号の文のすぐあと(または、足りないものの文の前)に 1 回だけ置く。山ごとの説明の中に入れない。
- 照合では位置を見ない(今のまま)。控えの文は、この位置になっていることを確かめる(なっていなければ直す)。
