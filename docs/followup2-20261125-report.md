## 利用者がやること(順番)

1. コンシェルのブランチを push する。
   - `! git -C C:/biyori-concierge push -u origin chore/collect-defaults`
   - `! git -C C:/biyori-concierge push -u origin feature/stale-forecast-wording`
2. PR の順: **先に `chore/collect-defaults`**、次に `feature/stale-forecast-wording`(手順の文書が、E2 の動きを前提にしているため)。`git merge-tree` で衝突がないことを確かめた。
   - どちらも、前回(C1〜C4)の commit を含みます。`docs/freshness-proposal` は前回のまま(境目の記述が古い)。
3. マージのあと、手動の取得で E2 を確かめる: Actions → collect → Run workflow で、`confirm` に `yes-run-live`、`yama_limit` に `3`、`publish` はチェックのまま実行する。collect の Summary に「棚は置き換えていません」「yama_limit を all にして」と出て、publish ジョブが skipped になれば正しい(通信は 3 座ぶん)。
4. 定期取得を on にする変数を足す(GitHub の画面):
   1. リポジトリ → **Settings** → 左の **Secrets and variables** → **Actions** → 上の **Variables**(Secrets ではない)→ **New repository variable**。
   2. (任意)Name `BIYORI_COLLECT_AGENTS`、Value `yamabiyori` → **Add variable**。
   3. Name `BIYORI_COLLECT_SCHEDULE`、Value `on` → **Add variable**。止めるときは値を `off` にするか、変数を消す。
5. 足したあとの確かめ方: 次の朝か夕の回のあと、Actions → collect で、event が schedule の回が skipped でなく緑か、publish も緑かを見る。`python -X utf8 -m concierge sync` と `status` で、時点が新しく、76 座のうち 76 座になっていることを見る。実際の起動時刻を数日ぶん控える(取得の時刻を変えるかは、それを見て決める)。
