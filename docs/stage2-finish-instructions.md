## 4. 第 1 部: 候補の選び方と並び(`concierge/brief.py`)

今の動き: 日ごとに、基準点以上の山を「点数の高い順・同点は山の ID の順」で上位 8 座。その中に主役にできる山が 3 座より少なければ、枠の外から足す(`main_ok_min`)。
困ること: 冬は上位が危険信号「警戒・危険」の高い山で埋まる。点数 100 の山が多い日は、どの山が資料に入るかが山の ID で決まる。

### 4.1 新しい選び方(日ごと)

1. **主役の枠**: 「主役にできる山」(基準点以上・危険信号が警戒未満・予報の中身あり。今の `main_ok`)だけを並べ、上位 `top_per_day` 座(8 のまま)を入れる。
2. **見送りの枠**: 基準点以上で、危険信号が「警戒」「危険」の山を点数の高い順に並べ、上位 `skip_per_day` 座(仮置き 3)を入れる。主役にできない印は今までどおり付ける。
3. 名指しの山は、今までどおり枠と別に必ず入れる。
4. `main_ok_min` と、枠の外から足す処理はやめる(`config.yaml` からも消す)。
5. 外した山の理由ごとの件数は、新しい枠に合わせて数え直す(主役の枠の外・見送りの枠の外)。

### 4.2 並び(同点の扱い)

主役の枠の並びは、次の順にする。

1. 点数の高い順。
2. 危険信号の軽い順(なし → 注意)。危険信号が 2 つ以上あるときは、数の少ない順。
3. 出発地からの直線距離の近い順。
4. 山の ID の順。

見送りの枠は、点数の高い順 → 直線距離の近い順 → 山の ID の順。

2 と 3 は好みの仮置きです(安全を先に、次に近さ)。`config.yaml` にそう書く。

### 4.3 順位の表記

事実の「その日の順位」は、同点を同じ順位にする(100 点が 5 座あれば、5 座とも 1 位。次は 6 位)。`say` の表記も「1位(同点 5 座)」のように、同点があると分かる形にする。
`plans`(主役にできる山の案)の並びは、4.2 の主役の枠の並びと同じにする(今は日付 → 距離 → ID)。

### 4.4 テスト

- 上位の点数の山が全部「警戒・危険」の日でも、主役にできる山が `top_per_day` 座まで資料に入る。見送りの枠には、高得点の危険な山が `skip_per_day` 座まで入る。
- 同点の山の並びが、危険信号の軽さ → 距離 → ID の順になる(山の ID だけで決まらない)。
- 同点の順位が同じになる。
- 同じ入力・同じ `--now` で資料が変わらない(今あるテスト)。
- `main_ok_min` を確かめている既存のテストは、新しい動きに合わせて直してよい(2 章の例外)。

## 5. 第 2 部: 決まった文と言葉の直し

### 5.1 危険信号の注記を 1 回にする

今は、山ごとの危険信号の文の終わりに毎回「(危険信号は点数とは別の警告です)」が付く。問い 1 の答えでは 5 回出た。

- 山ごとの危険信号の文(`_hazard_line`)から、この注記を外す。
- 注記は、別の決まった文 1 つにする(例: 「危険信号は、点数とは別に出る警告です。」)。資料に危険信号つきの山が 1 つでもあれば、この文を `lines` に入れる。
- 照合: 答えに危険信号の文が 1 つでもあれば、この注記の文が 1 回あること。2 回以上あっても不合格にはしない。
- 控えの文も同じ形にする。

### 5.2 「雲量(較正後)」を「雲量」にする

答えに出る名前を「雲量」にする。較正後の値であること(ヤマビヨリが採点に使う実効雲量)は、`docs/brief-fields.md` に残す。資料の Markdown には、AI が読む注として 1 行あってよい(答えには書かせない)。
ほかの値の名前に、答えにそのまま出ると分かりにくい語(「較正」「生」「CAPE」など)があれば、`docs/brief-fields.md` の表に「答えに出る名前」の列を足して整理する。**言い換えは、ヤマビヨリの README・手順書にある言い方の範囲で行う。** 範囲の外になる言い換えは行わず、報告書に候補として並べる。

### 5.3 予報の範囲の外の日

対象の日のうち、一部の日だけ予報が無いとき(例: 土曜はあるが日曜が無い)に、「足りないもの」にその日が入り、控えの文にも出ることを確かめる。出ていなければ直す。

### 6.2 比べる文(いちばん・最も)を資料と照らす

今は、「候補の中で稜線の風がいちばん弱い」のような文の中身を照らしていない。

- 資料(`brief`)が、日ごとに「比べた結果」の事実を作る。対象は、主役の枠の山の中での次のものだけ: 稜線の風がいちばん弱い山、出発地からいちばん近い山。同じ値の山が 2 つ以上あるときは、その事実を作らない(言い切れないため)。
  - 事実の id は今の形に合わせて決める(例 `C1`〜。印の正規表現に足す)。`say` に、書いてよい言い方を持たせる(例: 「主役の候補の中で稜線の風がいちばん弱い」)。
  - 対象を増やすのは、実際の質問を見てからにする(仮置き)。
- 照合: 最上級の語(いちばん・一番・最も・もっとも・最〜 のうち、仮置きの一覧)と、比べる対象の語(風・近い・遠い・高い・低い・点数 など。仮置き)が同じ文にあるとき、比べた結果の事実の印が要る。印の事実が言っている山・対象と合わなければ不合格。
- 「点数がいちばん高い」は、順位の事実(4.3 の「1位」)の印があれば通す。同点があるときに 1 つの山だけを「いちばん高い」と書いたら不合格。
- 見送りを言う文も、同じ検査を当てる(今は `recommend_not` で外しているのは、おすすめの語の検査だけ)。

## 8. 第 5 部: 取得の側 — 429 の種類を記録に残す(別の commit)

2026-11-23 0:23 の手動実行は、最初の通信が 429 で、0.4 秒で終わった。判定は設計どおり(`rate_limited`、棚は前回のまま)だったが、**1 分・1 時間・1 日のどの上限だったかが記録に残っていない**。GitHub のマシンは出口の IP を他の利用者と共有するので、この種類が分からないと対策を決められない。

- 計測フックは、非 200 の応答の本文の先頭 200 文字を、記録の `body_head` に残している(フックは変えない)。
- 取得の側(`collect/runner.py`・`collect/run.py`)で、429 の記録の `body_head` から種類を決める。決め方はヤマビヨリの `classify_rate_limit()` と同じ(大文字小文字を区別せず、`daily` → `hourly` → `minutely` の順に語を探す。どれも無ければ `unknown`)。ヤマビヨリのコードは import しない・写さない(同じ規則を書き、出典をコメントに書く)。
- 種類ごとの回数(例 `{"hourly": 1}`)を、回ごとの記録・`run.json`・manifest・`logs/requests.json` に足す(スキーマは項目を足すだけ)。**本文そのものは棚に載せない**(種類の回数だけ)。
- 実行のまとめの文(`collect/shelf.py`)の「429:」の行に、種類を出す(例: 「429: yamabiyori 1 回(1 時間の上限。rate_limited。取り直しの回は始めず、棚は前回のまま)」)。
- テストを足す(本文の例から種類が決まる・本文が無ければ `unknown`・棚に本文が入らない)。
