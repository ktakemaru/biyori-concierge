## 3. 接続の段階の失敗か、応答待ちの失敗か

**言える**:
- 90 件はすべて requests の `ReadTimeout`。requests は TCP の接続が時間内にできないときは `ConnectTimeout`、接続を拒否されたときは `ConnectionError` を出す。そのどちらも 0 件。
  つまり、**TCP の接続が時間内にできなかった失敗は、記録上 0 件**。
- 429 もほかの 4xx/5xx も 0 件(応答の状態コードを受け取れた失敗はない)。
- メタデータの 1 件は、別の経路(urllib)で、**TLS のハンドシェイクの時間切れ**と記録されている(30 秒)。

**未確認**:
- 90 件の `ReadTimeout` が、TLS のハンドシェイクの途中で起きたのか、リクエストを送ったあと応答を待っている間に起きたのか。
  記録には段階ごとの時間が無く、区別できない。urllib3 の版によっては、ハンドシェイクの時間切れも `Read timed out` として出るとされるが、
  この実行の venv の urllib3 の版と、その動きは確かめていない。
- 相手がリクエストを受け取ったか、応答を途中まで返していたか(失敗した通信の受信バイト数は記録していない)。
- メタデータの 1 件(TLS のハンドシェイク)と 90 件が同じ原因かどうか。
- 失敗の原因そのもの(相手側の混み具合、429 を返さない制限、GitHub のマシンからの経路、出口 IP の共有など)。記録からはどれとも決められない。

## 6. 全座そろわない回を棚に載せるか(**決定: A**。載せる。状態 incomplete と coverage つき)

決める前の検討(残しておく)。今の動き(`collect/shelf.py` の `PUBLISHABLE`): 載せる。manifest の `status` は `ok` でなく `incomplete` にし、`coverage`(何座のうち何座)を付ける。
collect ジョブは赤になる(`verdict`)。publish ジョブは `always()` なので、それでも動く。

| 選択肢 | 良い点 | 困る点 |
|---|---|---|
| A. 載せる(今の暫定) | 取れた山は新しい予報になる。どの回でも棚が更新される | 取れなかった山が棚から消える(前回のその山の予報も消える)。回によって山の数が変わり、答える側が `coverage` を見て「何座は調べられていない」と言う必要がある |
| B. 前回を残す(`kept_previous`) | 棚には、いつも 1 回の取得でそろった組だけが載る。答える側が簡単 | この回のような失敗率だと、そろう回が少なく、棚が長く古いままになりうる。最初の 1 回がそろわなければ棚に山が無い |
| C. しきい値で分ける(例: 9 割以上なら載せる) | 数座の欠けは許し、大きな欠けは前回を残す | しきい値の根拠がない(仮置きになる)。載せた回は A と同じく欠けた山が消える |
| D. 欠けた山だけ前回の値で埋める | 棚の山がいつも全座そろう | 1 つのファイルに、取得した時刻・予報の回が違う山が混ざる(山どうしの比べ方が変わる)。ヤマビヨリの出力をそのまま載せる今の作りを崩し、山ごとの時刻を持たせる作業が要る |

棚の決まりとは別に、欠けを減らす方向(取れなかった山だけ取り直す・打ち切りの時間を変えるなど)もある。どれも通信の量やヤマビヨリの動きにかかわるので、今回は手を付けていない。

## 7. 取り直しで、取れた山が通信なしになるか(コードで確かめたこと)

ヤマビヨリ commit `b0183552217c9dc116547c272f3b4192f44f6ea0` の `mountain_weather_core.py`(`fetch_open_meteo`・`_cache_path`・`_save_cache`)を読んだ。

**言える(コードから)**:
- Open-Meteo への通信は、すべて `fetch_open_meteo` を通る。応答はチェックアウトの `cache/` に、(緯度・経度・モデル・日数)ごとに 1 ファイルで保存される(`{model or 'best_match'}_{lat:.4f}_{lon:.4f}_{days}d.json`)。
- 保存は、1 回の通信が成功するたびにすぐ行われる(山の 3 回の通信がそろうのを待たない)。だから、1 回目で A・B が取れて C で飛ばされた山は、2 回目には C だけを取りに行く。
- 保存から 3 時間未満(`CACHE_TTL_SECONDS`)で、要る変数が全部ある場合は、通信しないでファイルを返す。
- 取り直しは同じジョブの同じチェックアウトで、すぐあとに実行するので、3 時間の内側。

**確かめ方(計測フックの数)**: 取得の結果と manifest の `attempts` に、回ごとの通信の数(計測フック)と `fetched` を出す。
2 回目以降の通信が「前の回に欠けた山 × 3 回の通信 × ヤマビヨリの 3 回の試行」を超えたら、`cache_suspect: true`(キャッシュが効いていない疑い)と表示する。

**未確認**: 実際の GitHub のマシンで、2 回目の通信が欠けた山の分だけになるか(取り直しを入れた実行の記録で確かめる)。
