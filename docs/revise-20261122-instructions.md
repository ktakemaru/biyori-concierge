**6.2 資料(スキーマ `biyori-brief/1` を新しく定義する)**

資料は、その質問のために集めた「確かめ済みの事実」です。次のものを入れる。

- `question`・`now`・解決した日付(`when`)・出発地。
- `candidates`: 山(段階 2)・星(段階 3)・生き物(段階 4)の候補。棚の `proposals/*.json` を対象の日・地域・興味・250km で絞ったもの。候補は消さず、外した理由(範囲外・対象の日でない・基準未満など)を残す。候補ごとに、答えに書いてよい事実(日付・時刻・数値・地名・状態の語・出典)を持たせる。
- `plans`: 組み合わせの候補(6.3)。
- `lines`: **そのまま写す決まった文**。
  - `lines.data_time`: 例「山と星の予報は 11/14(土) 4:38 時点のものです(気象庁 MSM は 11/14 0時の回)。」棚が半日以上古いときは、その旨が入る。
  - `lines.coverage`: 山について、**76 座のうち何座を調べたか**を必ず言う(manifest の `coverage`)。全座そろった回も言う。`status: incomplete` のときは、調べていない山がある旨が必ず入る。
  - `lines.lead_time`: 対象の日が、ヤマビヨリの「信用してよい範囲(3日前まで)」の外なら「○日先の予報で、傾向として読んでください。」など。境界の日数は各ビヨリの README・SKILL の記述から取り、出典を `config.yaml` に書く(推測で決めない)。

  - `lines.attribution`: Open-Meteo の帰属表示など、省けない文。
- `cards`: 知識カード(出典つきの「なぜ」)。初版は少なくてよい。「判断を変える知識」(例: 季節の通行止め、ロープウェイの運行の時期)から足す。カードが 0 枚でも動くこと。

**6.5 答えの形と照合**

手順: `sync` → `brief` → エージェントが資料を読んで下書きを書く → `verify`。不合格なら理由を読んで直す(**2 回まで**。イキモノビヨリと同じ)。それでも通らなければ、`verify` が資料から作る控えの文(事実だけの骨組み)を出す。
最後に送るのは `verify` が出した文だけ(前にも後ろにも何も足さない)。

答えの形(スマホで読める長さ。上限は 2,000 字を仮置き):

1. 冒頭 1〜2 文で結論(いちばんのおすすめと、その理由。見送るのがよければそう言う)。
2. `lines.data_time`(いつ時点の予報か)。
3. おすすめ ①②③(3つまで): 主役 → 添えるもの → 理由(なぜ今・なぜそこ)→ 注意(危険信号・確かさ)。
4. 今回は見送ったほうがよいもの(あれば 1〜2 行)。分からなかったこと(`gaps`)。
5. 出典と帰属(`lines.attribution` をそのまま)。

**主張の種類と扱い(照合の中心。D9)**

| 種類 | 例 | 扱い |

| B. AI の知識で書いてよい | 一般的な知識、名前の由来、楽しみ方、なぜその季節に見られるかの一般的な説明、景色の見どころ | 書いてよい。知識カードで裏が取れたものは出典つき。取れないものは「一般に知られている話」と分かる書き方にする。確かさの段の語は、イキモノビヨリの `docs/guide-voice.md`「確かさの3段」と同じ語を使う |
| C. 山の安全に関わる判断 | 行ける・引き返す、必要な装備、難しさ、凍結・積雪・ルートの状態、所要時間 | AI の知識だけでは書かない。資料の危険信号・予報の数字と、出典つきの知識カードがあるものだけ。無ければ「この資料からは判断できません」と書く |

- 生き物の見分け方・特徴は、イキモノビヨリの決まりに合わせて、出典つきのカードにあることだけを書く(A と同じ扱い)。

## 6. 第 3 部: 計測フックが 429 を決まった回数まで通す(別ブランチ)

`git switch -c feature/hook-tolerate-429`(第 2 部を commit したブランチの先頭から)。

### 6.1 考え方

今は、フックが 429 を見た瞬間に子プロセスを止める(終了コード 75)。そのため、ヤマビヨリが「1 分の上限なら 65 秒待って取り直す」前に終わってしまう。
フックは 429 の種類(1 分・1 時間・1 日)を判定しない。**種類の判定と待つ・やめるの判断はビヨリに任せ、フックは回数の上限だけを守る。取得の側は、結果(全部の山がそろったか)で判定する。**

### 6.2 `collect/measure/sitecustomize.py`

- 新しい環境変数 `BIYORI_HTTP_429_MAX_TOTAL`(実行全体で通す 429 の回数)を足す。
  - 未設定なら、今までどおり(429 は 1 回で即中止)。**既定の動きを変えない。**
  - 1 以上の整数のときだけ有効。不正な値・0 以下は無効にして、その旨を標準エラーに 1 行出す(今の `BIYORI_HTTP_RETRY_*` と同じ流儀)。
  - 上の限りを 1 つ持つ(仮置き 10。これより大きい値は拒否して無効にする)。暴走を止めるための安全弁なので、大きな値を受け付けない。
  - 通した 429 は、記録に印(今の `retry_tolerated` に合わせた名前)を付ける。回数を超えた 429 は、今までどおり即中止し、理由に「429 を通す回数の上限を超えた」と分かる文を入れる。
- **今の `BIYORI_HTTP_RETRY_STATUSES` の仕組みには 429 を足さない**(`_RETRYABLE` は 502・503・504 のまま。既存のテスト `test_429_is_never_tolerated_even_if_opted_in` はそのまま通ること)。
- 429 以外の 4xx・5xx の扱い、許可ホスト、件数の上限、壁時計の検査は変えない。
- ファイルの先頭の説明(中止の条件の一覧)を直す。`docs/ported-from-hub.md` に、hub から写したあとに変えた点として書く。

### 6.3 `collect/runner.py`・`collect/run.py`

- `config.yaml` の `collect.agents.yamabiyori` に、通す 429 の回数を足す(値は 5。コメントに出典: ヤマビヨリ `mountain_weather_core.py` の `MINUTELY_RETRY_MAX = 5`)。`C:/yamabiyori` の実物の値が 5 でなければ、実物に合わせる。
- `run_hooked()` が、その値を `BIYORI_HTTP_429_MAX_TOTAL` として子プロセスに渡す(設定が無い・0 なら渡さない)。親の環境の同じ名前の変数は、今の `BIYORI_*` と同じく捨てる。
- 判定を直す(5.2 の改訂と同じ内容)。
  - 429 の記録が無い回: 今までどおり。
  - 429 の記録があり、フックに止められず、終了コード 0 で、出力が正しく、`fetched` = `pool_size`: **成功**(待って取り直せた回)。
  - 429 の記録があり、それ以外(フックに止められた・終了コードが 0 でない・出力が無い・`fetched` < `pool_size`): `rate_limited`。**取り直しの回を始めない。** そのビヨリは今までどおり `kept_previous`。
- 429 の回数を、回ごとの記録(`attempts[]`)と全体の集計に残す。`run.json`・manifest・`logs/requests.json` のスキーマに項目を足すときは、足すだけにする(今ある項目の名前と意味を変えない。スキーマ名の番号は上げない)。
- 実行のまとめの文(`collect/shelf.py` の「429: あり / なし」の行)を、「429: 2 回(待って取り直し、全座そろった)」のように、回数と結果が分かる文に直す。

### 6.4 時間の上限

65 秒 × 5 回 = 325 秒が、1 回の実行に足されることがある。今の時間の上限(2700 秒)の内側に収まる。上限の値は変えない(U8 の実測のあとで利用者が決める)。

### 6.5 足すテスト(通信なし)

- フック: 変数なしなら 429 は 1 回で中止(今のテストのまま)。変数 2 なら、2 回までは通し、3 回目で中止。不正な値・上の限りを超える値は無効。502 などの扱いは変わらない。
- 取得の側(見本の子プロセスで):
  - 429 が 1 回あって全部の山がそろった回は `ok`。429 の回数が記録に残る。
  - 429 があって山がそろわなかった回は `rate_limited`。取り直しの回が始まらない(子プロセスの起動が 1 回だけ)。
  - 通す回数を超えた回は、フックの中止で `rate_limited`。
  - 設定を外すと、今までと同じ動き。

### 6.6 既存のテストの扱い

`tests/test_retry.py`・`tests/test_collect_run.py`・`tests/test_shelf.py` には、「429 なら `rate_limited`」を確かめるテストがある。`config.yaml` に通す回数を入れたことで、これらの見本の子プロセスの動きが変わるかもしれない。

- 期待値(`rate_limited` など)は書き換えない。
- どうしても通らないテストは、そのテストに「429 を通さない設定」を渡す変更だけは行ってよい(今までの動きの確かめとして残す)。行ったテストの名前を報告書に並べる。
- それでも通せないときは、止まる条件 5。

### 6.7 文書

- `README.md` の「429 で即中止します」を、新しい動きに直す。
- `CHANGELOG.md`、`collect/runner.py`・`collect/run.py`・`collect/diag_probe.py`・`collect/meta_fetch.py` の中の「429 は即中止」という説明のうち、変わったところを直す(メタデータの取得と診断は、通す設定を渡さないので今までどおり。そのことを書く)。
